# 发现页"为你推荐"三端统一智能推荐（纯服务端改造，三端前端零修改）

## 现状（问题根源）

- 该模块无独立推荐接口：web 走 `getEditorPicks()`（`isEditorPick=true` 按录入时间倒序取 8）；Android/小程序走 `GET /api/podcast/list` 全量 + 客户端 `filter(isEditorPick)` 取前 6，而**该接口无 orderBy，顺序为数据库任意序**——三端不一致且不可控。
- 候选池纯人工勾选，热度/新鲜度/用户画像完全不参与；精选不足时模块显示不满。

## 方案（已确认：打分+自动补位+个性化+水平等级参考，固定排序）

### 1. 新增统一推荐服务 `lib/discover-recommend.ts`

`getRecommendedPodcasts({ userId?, limit=8 })` → 有序推荐列表（含全部现有展示字段），供 web 与 API 共用，保证三端结果一致。

**候选池**：`coverFileName != null` 的全部播客（与现有接口口径一致），带出 totalPlays / followerCount / createAt / isEditorPick / tags / 剧集计数 / 最新一集 publishAt。

**打分公式**（对数压缩，权重为模块内常量，便于调参）：

- 运营加权：`isEditorPick` +40
- 热度：`log10(1+totalPlays)×8 + log10(1+followerCount)×6`
- 更新新鲜度：最新一集距今 d 天——30 天内 `20×(1-d/30)`，30~90 天线性衰减至 0，超 180 天 -10（弃更降权）
- 内容完备度：`min(episodeCount,30)/30 × 10`
- 冷启动：createAt ≤30 天 +8

**个性化（有 userId 时）**：

- 排除已收藏（`podcast_favorites`）
- 近 30 天听过（`listening_history` join episode）降权 -15
- 难度匹配 +25×占比：用户等级取 `speechProfileService.getDerivedLevel(userid)` 优先、回退 `user_profile.learnLevel` 经 `LEVEL_MAPPING`/`CEFR_EPISODE_MAPPING`（复用 `core/episode/episode.service.ts:33` 的映射，提升为共享导出）映射出目标难度集，计算该播客已发布剧集命中难度占比（一次 `episode groupBy [podcastid, difficulty] where status=published` 聚合）
- 未登录/画像缺失 → 纯全局分（优雅降级）

**多样性与确定性**：同一 platform 最多 2 个（round-robin 延后装填）；并列按 totalPlays desc → podcastid asc；无随机、无时间抖动，刷新稳定。

### 2. 投放路径（接口形状全部不变）

- **web**：`app/(main)/discover/page.tsx` 加 `auth()`（`@/auth`）取 userid；`getEditorPicks()`（`lib/discover-service.ts:360`，唯一调用方即发现页）改为内部调用推荐服务，返回结构（签名 coverUrl/category/episodeCount）不变，仍取 8。
- **`GET /api/podcast/list`**（`app/api/podcast/list/route.ts`）：
  - 用现有 `authWithMobile()`（`core/auth/guard.ts:113`，cookie + Bearer 双通道 best-effort）识别用户，失败即未登录逻辑
  - **响应数组重排**：推荐 top 8 在前（推荐序），其余按 totalPlays desc
  - **响应中 `isEditorPick` 重算**为"是否属于推荐集"（恰前 8 个为 true）→ Android/weapp 现有 `filter(isEditorPick).take(6)` 展示的就是个性化推荐前 6、顺序正确
  - 路径、参数（无）、字段、裸数组结构完全不变；热门榜/新节目/频道为客户端独立排序不受影响；"全部播客"网格由任意序变推荐序在前（属改善）；管理端不经此接口，DB 中 `isEditorPick` 原值不动
  - 保持无缓存（个性化要求）

### 3. 验证脚本 `scripts/test-discover-recommend.ts`

只读：打印未登录/登录两套推荐 Top10 及分数构成，校验推荐序与 `/api/podcast/list` 前 8 一致、标记数=8。

## 验证步骤

1. `npx tsc --noEmit` + eslint 通过
2. 跑验证脚本核对分数与顺序
3. dev server 下 curl `/api/podcast/list`（带/不带 Bearer）确认顺序与 isEditorPick 标记、字段结构 diff 仅顺序与标记
4. web /discover 页渲染前 8 与 API 前 8 一致；三端（weapp/android 代码走查，不修改）`filter+take` 行为符合预期

## 边界

- 新增 3 个轻查询（仅登录时：favorites / 近期 listening_history / 难度聚合），数据量万级可接受
- 全池为空 → 模块隐藏（与现状一致）；推荐不足 8 个时按分全量补位
- 实现时留意 memory 坑：服务端调用需透传会话 role 的场景此处不涉及（推荐不做付费判断）
